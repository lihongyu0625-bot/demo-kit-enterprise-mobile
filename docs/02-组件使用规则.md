# 组件使用规则

这份规则不是写给程序员看的“很硬的规范”，而是给你后面自己扩页面、交给同事继续做时防止混乱的。

## 一、先分清三种文件

1. `src/components`
   放组件本身
2. `src/pages`
   放页面组装入口
3. `src/page-specs` 和 `src/mock-data`
   放页面顺序和演示数据

简单理解：

- 组件文件负责“长什么样”
- 页面文件负责“怎么拼起来”
- 配置文件负责“顺序和内容”

## 二、组件编写规则

1. 一个组件只做一件事  
   例如导航栏只负责导航栏，不要顺便把整页逻辑塞进去。
2. 组件尽量通过入参拿数据  
   不要把酒店名、价格、手机号直接写死在组件里。
3. 相同结构先抽基础件  
   例如卡片壳、分割线、字段行，应该优先复用。
4. 页面顺序不要写死在组件里  
   用 `page-specs` 控制顺序，后面改版更省事。
5. 演示数据不要写进页面文件  
   用 `mock-data` 管理，后续换成真实接口时更容易替换。

## 三、命名规则

1. 基础组件  
   用“能力名”，例如 `Checkbox`、`PriceDisplay`
2. 业务组件  
   用“业务 + 卡片/区域”，例如 `HotelRoomInfoCard`
3. 页面组件  
   用“页面名 + PreviewPage` 或 `Page`”，例如 `HotelFormPreviewPage`

## 四、样式规则

1. 样式统一放在同目录的样式文件里
2. 不要在组件里大量写内联样式
3. 类名尽量带上业务前缀  
   例如 `hotel-card`、`hotel-toolbar`
4. 同一个页面的样式先集中管理  
   当前放在 `hotel-form.css` 是可以的

## 五、什么时候要继续拆组件

出现下面任意一种情况，就该继续拆：

1. 同一个结构在两个页面里重复出现
2. 一个组件的入参超过 5 组以上
3. 一个组件里既有布局，又有很多业务判断
4. 同事看这个组件名字时，不能一眼知道它干什么

## 六、上传云端前必须做到的事

1. 每个组件有明确名字
2. 每个组件知道自己吃什么数据
3. 每个组件能单独预览
4. 页面和组件分开
5. 样式文件位置固定

## 七、你现在就可以怎么做

你现在不用一下子把全部组件都“工程化”，先按这个顺序：

1. 先确认这页能正常展示
2. 再把基础组件单独拆文件
3. 再给每个组件补一行用途说明
4. 最后再准备上传云端

## 八、当前这套代码下一步最值得做的事

优先级最高的是这两件：

1. 把基础组件从 `HotelFormComponents.jsx` 里拆出来
2. 把部分写死的中文文案继续改成入参

这样做完后，云端复用价值会明显更高。
